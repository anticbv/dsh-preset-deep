# 长任务检查点

上下文会被压缩，文件不会。压缩后接不上，等于任务失败——哪怕中间每一步都对。

## 什么时候写

满足任一条就开检查点文件（工作区里，不要只留在对话里）：

- 预计跨两次以上工具往返，或跨多个会话
- 任务有多个阶段，每阶段有自己的验收
- 中途可能被压缩、被中断、被换人接手

一句话任务的不要建，直接做完。

## 五个字段

```markdown
## 目标
一句话，含被点名要改的东西与不许碰的范围。

## 完成条件
具体到命令或断言。不是「做得好」，是「跑这条命令得到这行输出」。
验证不得只由自己新写的测试构成——先有独立证据，再看自己的测试。

## 已完成并验证
- [x] 做了什么 —— 证据：命令 / 文件:行 / 哈希

## 决策与教训
- 选了什么、为什么不选另一个（「因为」是承重的）
- 走过的死路：试了什么、为什么不行（防止重试）

## 下一步
下一步具体动作，以及卡在哪、需要谁定。
```

每完成一个阶段立刻更新，不要攒到最后补写——攒到最后一定会丢。

## 压缩之后的核对清单

1. 先读检查点，核对完成条件是否仍成立（目标可能已被用户改过）
2. 已完成并验证的项不要重做；不确定是否真完成，回到证据那行复核
3. 要引用检查点里记的原文，先恢复原段再引用，不要拿摘要转述
4. 检查点里没有的结论当作没做过，重新取证或标未知

## 偏航检测

出现下列情况时停下来写一行诊断，再决定继续或回头：

- 正在做的事不在「下一步」里
- 完成条件的验证方式被悄悄换成了一个更容易的断言
- 连续两次失败还在试同一条路径
- 范围外的东西开始被顺手改动

诊断写进「决策与教训」，不要只留在脑子里。
